# ТЗ на вторую контрольную точку: RAG и benchmark

Документ распределяет работу к точке 2 между тремя участниками. У каждого своя зона, свои файлы и свой критерий готовности. Части связаны через контракты из раздела [Контракты между частями](#контракты-между-частями), поэтому все работают параллельно и не ждут друг друга.

## Что требует преподаватель

По материалам занятия 3 «RAG и BM25» и методическим указаниям к НИРС (раздел 2) к точке 2 нужно три результата:

| № | Результат | Что это значит для нас |
| --- | --- | --- |
| 1 | Работающий RAG | Вопрос → поиск BM25 → LLM отвечает по найденным фрагментам. Если сведений нет — система отказывается отвечать. **BM25-индекс пишем сами**, готовые поисковые индексы (`rank-bm25` и т. п.) запрещены |
| 2 | Benchmark | 30 документов `D01…D30`, 10 обычных вопросов (у каждого **не меньше 3 релевантных документов** и эталонный ответ), 5 вопросов-ловушек (ответа в корпусе нет). Результаты, 4 метрики и короткий разбор ошибок |
| 3 | README | Как запустить систему и повторить проверку |

Дополнительное требование преподавателя: **во время сдачи точки 2 benchmark должен запускаться в рантайме**, то есть прямо на защите, а не показываться готовым файлом.

### Метрики benchmark

| Метрика | На каких вопросах | Как считается |
| --- | --- | --- |
| Recall@k | 10 обычных | Доля релевантных документов, найденных в первых k: `|R ∩ Top_k| / |R|`, среднее по вопросам |
| MRR@k | 10 обычных | Среднее `1 / rank` первого релевантного документа; если его нет в top-k — 0 |
| Accuracy | 10 обычных | Доля полностью правильных ответов LLM |
| Correct Rejection Rate | 5 ловушек | Доля вопросов, на которые система корректно отказалась отвечать |

Ловушки не входят в метрики поиска. Договорились: **k = 5**, MRR считается на той же глубине k = 5. Ранжирование для метрик идёт по документам: документ занимает позицию своего лучшего фрагмента в выдаче.

## Корпус для точки 2

Материалы **1 курса, 1 семестра** (матанализ, аналитическая геометрия, информатика, основы программирования, начертательная геометрия и др.). Исходники собраны у Темирлана локально и в Git не коммитятся, в репозитории — `manifest.json` и извлечённый текст.

Правила отбора 30 документов:

- у документа есть текстовый слой (сканы без текста не берём);
- темы пересекаются: на каждый обычный вопрос в корпусе должно найтись минимум 3 документа с ответом;
- никаких персональных данных студентов: чужие отчёты с ФИО, номерами групп и вариантами не берём или берём без титульных листов;
- у каждого документа есть ID `D01…D30`, название, дисциплина и тип.

## Темирлан — RAG: корпус, BM25, benchmark

### R1. Корпус `D01…D30`

- Отобрать 30 документов 1 семестра по правилам выше.
- `corpus/manifest.json`: `corpus_version`, список документов с полями `doc_id` (`D01`…), `title`, `discipline`, `doc_type`, `source` (относительный путь к исходнику), `pages`, `sha256`.
- Скрипт извлечения `python -m corpus.extract --source <папка с материалами>`: PDF постранично (`pypdf`), DOCX по абзацам (`python-docx`), результат — `corpus/processed/Dxx.jsonl` (одна строка = одна страница: `doc_id`, `page`, `text`).
- `corpus/processed/` коммитится, чтобы индекс можно было собрать без исходников.

**Готово, когда:** 30 документов в manifest, у каждого непустой текст, номера страниц совпадают с оригиналом.

### R2. Предобработка и собственный BM25

- `search/tokenizer.py`: нижний регистр, удаление пунктуации, лемматизация `pymorphy3`, стоп-слова; числа и обозначения («ЛР3», «ГОСТ 7.32», «2x») сохраняются. Один токенизатор для запроса и корпуса. Выбор лемматизации и токенизации обосновать в `spec/tech/rag.md` (требование методички).
- `search/chunker.py`: фрагменты по страницам и абзацам, ориентир 500–1500 символов, в текст фрагмента добавляется название документа.
- `search/bm25.py`: **свой** обратный индекс `терм → {фрагмент: tf}`, длины фрагментов, `avgdl`, формула BM25 с `IDF = ln(1 + (N − df + 0,5) / (df + 0,5))`, параметры `k1 = 1,2`, `b = 0,75`. Без `rank-bm25` и других готовых индексов.
- `python -m search.build` строит индекс и сохраняет его в `search/index/`; функция `retrieve()` — см. [контракт](#c1-поиск--python-модуль-search).
- `tests/test_search.py` (pytest): ручной расчёт BM25 на 3 документах из занятия 3 (`A ≈ 0,940`), детерминированность, пустой запрос, запрос без совпадений, стабильный `chunk_id`.

**Готово, когда:** `python -m search.build` и `pytest` проходят; на вопрос из корпуса нужный документ в top-5.

### R3. Набор вопросов

- `benchmark/questions.jsonl` — 15 вопросов в [формате C2](#c2-набор-вопросов--benchmarkquestionsjsonl): `Q01…Q10` обычные, `T01…T05` ловушки.
- Обычные вопросы покрывают разные дисциплины корпуса, у каждого ≥ 3 релевантных документа, эталонный ответ и 2–4 ключевых факта для автопроверки.
- Вопросы формулируются своими словами, как спросил бы студент, а не копированием фрагмента текста (требование методички).
- Ловушки похожи на реальные вопросы студента, но ответа в корпусе нет (например, расписание консультаций, правила другой дисциплины).
- Сейран и Анна предлагают по 2–3 вопроса, Темирлан проверяет разметку по документам.

### R4. Скрипт benchmark

- `python -m benchmark.run` — прогон всех 15 вопросов **в рантайме**, параметры `--k 5`, `--mode retrieval|full`:
  - `retrieval` — только поиск: Recall@k и MRR@k, без LLM, отрабатывает за секунды;
  - `full` — поиск + ответ LLM через функцию Сейрана `answer()`: все 4 метрики.
- Автопроверка ответа: ответ верный, если в нём есть все ключевые факты вопроса (сравнение по леммам) и `finish_reason = ok`; отказ верный, если `finish_reason = no_context`. В отчёт попадает текст ответа для ручной перепроверки.
- Результат: таблица в консоли + `benchmark/results/<дата-время>.json` и `.md` (commit, версия корпуса, модель, параметры, метрики, выдача и ответ по каждому вопросу, время).
- Функция `run_benchmark()` для вызова из backend — см. [контракт C3](#c3-запуск-benchmark-из-кода).
- Подобрать на обычных вопросах порог BM25 для отказа без вызова LLM и передать его Сейрану (`search/config.py`).
- Короткий разбор ошибок в `benchmark/README.md`: где потеряли информацию — в базе, в поиске, в контексте или в ответе.

**Готово, когда:** `python -m benchmark.run --mode retrieval` печатает Recall@5 и MRR@5; `--mode full` при запущенной Ollama печатает все 4 метрики.

## Сейран — Backend и LLM

### B1. FastAPI-сервис

- `backend/app/` на Python 3.12 + FastAPI + Uvicorn, `backend/requirements.txt`.
- `POST /api/chat` и `GET /api/health` по [api.md](../spec/tech/api.md): проверка `message` (1–2000 символов), коды 400/503/500, CORS только для адреса frontend.
- Индекс загружается один раз при старте через `search.load_index()`. Пока индекса нет — работать на заглушке поиска с тем же форматом `Hit`.
- Запуск одной командой: `uvicorn backend.app.main:app --port 8000`.

### B2. LLM через Ollama

- Модуль `backend/app/llm.py`: запрос к `http://localhost:11434/api/chat`, настройки из переменных окружения `OLLAMA_URL`, `OLLAMA_MODEL`, таймаут; Ollama недоступна → 503.
- Выбрать модель, которая помещается в память ноутбука для защиты (кандидаты: `qwen2.5:3b`, `qwen2.5:7b`, `llama3.1:8b`), записать выбор и причину в [журнал решений](../spec/decisions.md).
- Prompt: роль ассистента кафедры; фрагменты `[1]…[k]` с названием документа и страницей; вопрос; «отвечай только по фрагментам, если ответа нет — ответь ровно `В документах нет этой информации`; не решай задания за студента».

### B3. Функция ответа и отказ

- `backend/app/rag.py`: `answer(question, history=None, k=5) -> Answer` — см. [контракт C4](#c4-ответ-rag--функция-answer). Её используют и `/api/chat`, и benchmark Темирлана.
- Отказ без вызова LLM, если лучший BM25-score ниже порога из `search/config.py`; отказ, если LLM вернула фразу об отсутствии информации. В обоих случаях `finish_reason = "no_context"`.
- `sources` формируются из metadata фрагментов («Название документа, стр. N»), а не из текста модели.

### B4. Benchmark через API — запуск на защите

- `POST /api/benchmark/run` с телом `{ "k": 5, "mode": "full" }` запускает `run_benchmark()` Темирлана в фоне и сразу возвращает `run_id`.
- `GET /api/benchmark/runs/{run_id}` — статус (`running`/`done`/`error`), прогресс `done/total` и, когда готово, результат в [формате C3](#c3-запуск-benchmark-из-кода).
- Одновременно идёт не больше одного прогона: повторный запрос во время прогона → 409.

### B5. Тесты и запуск

- `tests/test_api.py` (pytest, LLM и поиск подменяются заглушками): 200 с `text`/`sources`/`finish_reason`, 400 на пустой вопрос, 503 при недоступной LLM, запуск и статус benchmark.
- Раздел README «Запуск» для всех трёх частей: установка зависимостей, `ollama pull <модель>`, сборка индекса, запуск backend и frontend, запуск benchmark из консоли и из интерфейса.
- Обновить [api.md](../spec/tech/api.md) и [architecture.md](../spec/tech/architecture.md), если реализация отличается от контракта.

**Готово, когда:** на ноутбуке для защиты по README поднимаются Ollama, backend и frontend; вопрос из корпуса получает ответ с источником, ловушка — отказ; benchmark запускается запросом к API.

## Контракты между частями

Контракты фиксируются сейчас, до кода. Меняет контракт его владелец, предупредив остальных в Pull Request.

### C1. Поиск — Python-модуль `search`

Владелец: Темирлан. Потребители: Сейран, benchmark.

```python
from search import load_index, retrieve

index = load_index("search/index")          # один раз при старте
hits = retrieve(index, "Как найти предел функции?", k=5)
# hits: list[Hit], отсортирован по убыванию score
```

| Поле `Hit` | Тип | Пример |
| --- | --- | --- |
| `chunk_id` | str | `"D07-p12-c2"` |

| `score` | float | `7.43` |
