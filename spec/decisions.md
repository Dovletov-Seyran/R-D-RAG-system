# Журнал решений

| ID | Решение | Основание | Ограничение |
| --- | --- | --- | --- |
| D01 | BM25 как первый метод поиска | Требование курса; работает на CPU, легко объяснить | Чувствителен к формулировке вопроса |
| D02 | Лемматизация русского текста (pymorphy3) | Методички и вопросы на русском, много словоформ | Ошибки разбора редких терминов и сокращений |
| D03 | Python + FastAPI для backend и поиска | Один язык для API, индексатора и экспериментов | Производительность не критична для учебной нагрузки |
| D04 | Поиск — модуль внутри backend на первом этапе | Маленькая команда, меньше сервисов для запуска | При росте может понадобиться отдельный сервис |
| D05 | Локальная LLM через Ollama | Материалы кафедры не уходят во внешние API, нет платных ключей | Нужен компьютер с достаточной памятью или GPU |
| D06 | Статический frontend без сборки на точке 1 | Быстрый показ интерфейса без зависимостей | Нет компонентов и типизации; пересмотреть при росте |
| D07 | История диалогов в `localStorage` | Не нужна БД для MVP | История не переносится между устройствами |
| D08 | Источник = документ + страница из metadata | Студент может открыть методичку и проверить | Требует сохранять номера страниц при извлечении |
| D09 | `main` + короткие ветки задач + Pull Request | Три участника, частая интеграция | Требует регулярного review |
| D10 | Собственный BM25-индекс вместо `rank-bm25` | Методичка НИРС, раздел 2: готовые поисковые индексы запрещены | Свой код нужно покрыть тестами (сверка с ручным расчётом) |
| D11 | Корпус точки 2 — материалы 1 курса, 1 семестра, 30 документов `D01…D30` | Объём из требований точки 2; материалы уже собраны командой, темы пересекаются | Это не методички кафедры ИУ-5 целиком; корпус расширяется к точке 3 |
| D12 | Benchmark запускается в рантайме: CLI `python -m benchmark.run` и `POST /api/benchmark/run` | Требование преподавателя к сдаче точки 2 | Полный прогон с LLM на CPU занимает минуты; есть быстрый режим `retrieval` |
| D13 | Метрики точки 2: Recall@5, MRR@5, Accuracy, Correct Rejection Rate; ранжирование по документам | Требования занятия 3; эталоны размечены на уровне документов `Dxx` | Документ получает позицию своего лучшего фрагмента |
| D14 | LLM — `qwen3:4b-instruct` в Ollama | Ноутбук защиты MacBook Pro M3, 8 ГБ: модель 2.5 ГБ помещается в память вместе с backend и браузером; на benchmark точки 2 Accuracy = 1.0, ответ ~10 с | `qwen2.5:7b` и `llama3.1:8b` (~5 ГБ) на 8 ГБ памяти на грани; модель сравнивается в эксперименте E4 к точке 3 |
| D15 | Уточняющий вопрос ищется вместе с прошлым вопросом пользователя | Короткое «а как тогда…?» само по себе не проходит порог покрытия и получало бы ложный отказ | Если прошлый вопрос не по корпусу — отказ остаётся; есть ли ответ во фрагментах, решает LLM |
| D16 | Источники ответа — из metadata фрагментов, на которые сослалась модель (`[n]`) | Студент видит конкретные страницы, а не все 5 фрагментов; текст модели источником не считается | Если модель не поставила ссылок — показываются все переданные фрагменты |
| D17 | Формулы в ответе — текстом с символами Unicode, без LaTeX | Интерфейс выводит ответ как простой текст; `\varepsilon` нечитаем и не совпадает с ключевыми фактами benchmark | Модель иногда всё же пишет `\( … \)`; при переходе на Markdown-рендер правило пересматривается |

Смена решения записывается новой строкой с причиной и влиянием на API и проверки.
